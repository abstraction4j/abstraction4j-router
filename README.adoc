Abstraction4j Router keeps "which implementation should handle this call?" logic out of your business code.
You describe the abstraction as an interface, write one implementation per variant, and supply a small _finder_ that picks the right implementation for each call.
The library generates a router for the interface, a dynamic proxy that does the routing at runtime.

toc::[]

== Why

Code that has to deal with several variants of the same capability (carriers, payment providers, API versions, tenants) tends to end up looking like this:

[source,java]
----
public void processOrder(Order order) {
  // ...

  if (customer.useUps()) {
    upsClient.ship(toUpsShipment(shipment), toUpsAddress(shipTo), toUpsAddress(shipFrom));
  }
  else if (customer.useFedex()) {
    fedexClient.ship(toFedexShipment(shipment), toFedexAddress(shipTo), toFedexAddress(shipFrom));
  }
  else {
    uspsClient.ship(toUspsShipment(shipment), toUspsAddress(shipTo), toUspsAddress(shipFrom));
  }

  // ...
}
----

The routing obscures what the method actually does, and the same `if/else` chain gets copied wherever the capability is used.
With Abstraction4j Router the business code depends only on the abstraction:

[source,java]
----
public void processOrder(Order order) {
  // ...
  shipperService.ship(customer, shipment, shipTo, shipFrom);
  // ...
}
----

[[how-it-works]]
== How it works

You provide three things:

. An *interface* describing the abstraction.
. One *implementation* per variant.
. A *finder*, an `ImplementationFinder<T>` that picks the implementation for each call.

The library provides the fourth: a *router*, an object that implements your interface and, on every call, asks the finder which implementation should handle it and forwards the call there.
Business code depends only on the interface, so it can't tell the router from a single implementation.

[source,java]
----
public interface ShipperService {
  void ship(Customer customer, Shipment shipment, Address shipTo, Address shipFrom);
}

public class UpsShipperService implements ShipperService {

  private final UpsClient upsClient;

  public UpsShipperService(UpsClient upsClient) {
    this.upsClient = upsClient;
  }

  @Override
  public void ship(Customer customer, Shipment shipment, Address shipTo, Address shipFrom) {
    upsClient.ship(toUpsShipment(shipment), toUpsAddress(shipTo), toUpsAddress(shipFrom));
  }

  // toUpsShipment / toUpsAddress mapping omitted
}

// FedexShipperService and UspsShipperService follow the same pattern.
----

=== Finders

Most finders route on one argument of the call.
`RoutingImplementationFinder` does that declaratively: name the argument type, derive a key from it, and map keys to implementations.

[source,java]
----
ImplementationFinder<ShipperService> finder = RoutingImplementationFinder.builder(ShipperService.class)
    .byArgument(Customer.class, Customer::carrier)   // first parameter of type Customer
    .route(Carrier.UPS, upsShipperService)
    .route(Carrier.FEDEX, fedexShipperService)
    .otherwise(uspsShipperService)                   // optional default
    .build();
----

The same builder grows with your routing rules, so routing stays in one place instead of spreading back into the business code:

* *Several key sources*: try a `Customer` argument, then an `Order`, then the current context such as the SLF4J MDC.
* *Routing keys*: mark the parameter to route on with `@RoutingKey` when its type alone is ambiguous, such as one `String` ID among several.
* *Conditional routes*: choose between implementations for the same key at call time, for example behind a feature flag or for beta tenants.
* *Custom finders*: for any other rule, implement `ImplementationFinder` directly; it receives the invoked `Method` and its arguments.

All of these are described in link:abstraction4j-router-core/README.adoc[abstraction4j-router-core].

=== Routers

A router is created once, from the interface and its finder, and then used like any other implementation of the interface.
There are two kinds, with the same behavior (see <<behavior>>):

* *JDK routers* are plain `java.lang.reflect.Proxy` instances, for applications without a framework.
* *Spring routers* are Spring AOP proxies. In a Spring application they can be registered automatically: declare a finder bean, and every injection point of the interface receives the router.

[[choosing-modules]]
== Choosing modules

The library is split into modules so that each application pulls in only what it uses.
They build on each other, and every module brings in the ones it builds on, so you only ever add one:

----
abstraction4j-router-core          the finder API; no dependencies
 ├─ abstraction4j-router-jdk       JDK routers
 └─ abstraction4j-router-spring    Spring routers, @EnableSpringAbstraction
     └─ abstraction4j-router-spring-boot-autoconfigure   registers routers in Spring Boot
         └─ abstraction4j-router-spring-boot-starter     the auto-configuration plus Spring Boot
----

Pick the one that matches your application:

[cols="2,2,4",options="header"]
|===
|You are building |Add |Why

|A Spring Boot application
|link:abstraction4j-router-spring-boot-starter/README.adoc[`abstraction4j-router-spring-boot-starter`]
|One dependency and no configuration. A router is registered for every finder bean, works in GraalVM native images, and can be turned off with a property.

|A Spring Boot application or library that manages its Spring Boot dependencies itself, or your own starter
|link:abstraction4j-router-spring-boot-autoconfigure/README.adoc[`abstraction4j-router-spring-boot-autoconfigure`]
|The same auto-configuration, without the starter's dependency on `spring-boot-starter`.

|A Spring application without Spring Boot
|link:abstraction4j-router-spring/README.adoc[`abstraction4j-router-spring`]
|Add `@EnableSpringAbstraction` for automatic registration, or create routers yourself with `SpringAbstractionRouters`. Uses your application's Spring version.

|A plain Java application
|link:abstraction4j-router-jdk/README.adoc[`abstraction4j-router-jdk`]
|Routers from `JdkAbstractionRouters`, with no framework and no dependencies beyond the core.

|A library that only defines finders or routed interfaces
|link:abstraction4j-router-core/README.adoc[`abstraction4j-router-core`]
|Has no dependencies, and leaves the choice of router to the application that uses your library.
|===

In a Spring application, prefer the Spring router even though a JDK router would also work: it can be registered automatically, Spring recognizes it as an AOP proxy, and Spring AOT generates its native image hints.
The JDK router is a few tens of nanoseconds faster per call (see <<performance-and-caching>>), which rarely matters next to the work the implementation does.

Each module's README has its Maven and Gradle coordinates, its setup and its details.

[[getting-started]]
== Getting started with Spring Boot

Most applications use Spring Boot, so this is the complete setup for it.
For the other setups, follow the module links in <<choosing-modules>>.

. Add the starter.
+
.Maven
[source,xml]
----
<dependency>
  <groupId>dev.abstraction4j.router</groupId>
  <artifactId>abstraction4j-router-spring-boot-starter</artifactId>
  <version>0.1.0</version>
</dependency>
----
+
.Gradle (Groovy)
[source,groovy]
----
implementation 'dev.abstraction4j.router:abstraction4j-router-spring-boot-starter:0.1.0'
----

. Declare the finder as a bean.
Inject the implementations by their concrete types, not as `ShipperService`, which would be the router itself:
+
[source,java]
----
@Configuration
class ShippingConfiguration {

  @Bean
  RoutingImplementationFinder<ShipperService> shipperServiceFinder(UpsShipperService ups,
      FedexShipperService fedex, UspsShipperService usps) {
    return RoutingImplementationFinder.builder(ShipperService.class)
        .byArgument(Customer.class, Customer::carrier)
        .route(Carrier.UPS, ups)
        .route(Carrier.FEDEX, fedex)
        .otherwise(usps)
        .build();
  }
}
----

. Inject the interface wherever you need it:
+
[source,java]
----
@Service
class OrderService {

  private final ShipperService shipperService; // receives the router

  OrderService(ShipperService shipperService) {
    this.shipperService = shipperService;
  }
}
----

The auto-configuration registers a `@Primary` router named `shipperServiceFinderRouter`, so `OrderService` receives the router rather than one of the implementations.
The rules finders must follow, and how to exclude one, are in link:abstraction4j-router-spring/README.adoc#automatic-registration[abstraction4j-router-spring]; the `abstraction4j.router.enabled` property is in link:abstraction4j-router-spring-boot-autoconfigure/README.adoc[abstraction4j-router-spring-boot-autoconfigure].

== Requirements

* Java 21+
* Spring Framework 7.0.1+ for `abstraction4j-router-spring`
* Spring Boot 4.0+ for `abstraction4j-router-spring-boot-autoconfigure` and `abstraction4j-router-spring-boot-starter`

The library modules don't bring in Spring, so your application's Spring version is always the one used.
The starter is the exception: like every Spring Boot starter it depends on `spring-boot-starter`, and Spring Boot's dependency management keeps your application's version.
CI tests the oldest supported versions (Spring Framework 7.0.1, Spring Boot 4.0.0) and the versions in `gradle/libs.versions.toml`.

All modules use the group `dev.abstraction4j.router`.
Their public API is the types named in each module's README; everything else is internal and may change without notice.

[[behavior]]
== Behavior

Both router types follow the same contract.

Routing::
Every call asks the finder once for an implementation, then invokes the same method, with the same arguments, on that implementation.
This includes default interface methods; the implementation's override, or the default, runs as usual.

Arguments::
The finder always receives a non-`null` argument array; it is empty for methods without parameters.
Elements are `null` where the caller passed `null`, and for a Kotlin `suspend` function the last element is its `Continuation`.

No implementation::
If the finder returns `null`, the call fails with an `IllegalStateException` whose message names the method.

Exceptions::
Exceptions thrown by the implementation reach the caller unchanged, not wrapped in `InvocationTargetException`.
Exceptions thrown by the finder also propagate unchanged.

Object methods::
`equals`, `hashCode` and `toString` never reach the finder.
`toString` describes the router and its finder.
JDK-based routers compare by identity (`equals` is `==`, `hashCode` is the identity hash code); Spring-based routers use Spring AOP's proxy equality.

Thread safety::
Routers are thread-safe, and the finder may be called concurrently from many threads, so it must be thread-safe too.
`RoutingImplementationFinder` is immutable and thread-safe, provided its key extractors and suppliers are.

Visibility::
Interfaces don't need to be public; package-private interfaces, and implementations in other packages, work.

Invalid types::
Passing a class instead of an interface to `routerFor` throws `IllegalArgumentException`.

[[performance-and-caching]]
== Performance and caching

Each call on a router costs one finder call plus one reflective method invocation.
On a typical laptop that adds roughly 20 to 30 ns per call for the JDK router and 40 to 55 ns for the Spring router, compared with calling the implementation directly.
Measure on your own hardware with the JMH benchmarks in `benchmarks/` (see <<Building>>).

`RoutingImplementationFinder` keeps that cheap on its own.
It works out which parameter to route on once per method and caches it, so each later call only derives the key and looks it up in a hash map.

The router does not cache the finder's _result_ across calls, on purpose.
The right implementation usually depends on the arguments, so an implementation chosen for one call can be wrong for the next.

If deciding the route is expensive, for example a database or remote lookup, cache inside the finder, keyed by the value that actually determines the route:

[source,java]
----
Cache<Long, Carrier> carriers = Caffeine.newBuilder()       // or any bounded, expiring cache
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofMinutes(10))
    .build();

RoutingImplementationFinder.builder(ShipperService.class)
    .byArgument(Customer.class, (customer) -> carriers.get(customer.id(), carrierService::carrierFor))
    .route(Carrier.UPS, ups)
    .route(Carrier.FEDEX, fedex)
    .build();
----

* If the route depends only on the method, not the arguments, it's safe to memoize per `Method` (for example with `ConcurrentHashMap.computeIfAbsent`), because the set of methods is fixed.
* Don't key a cache on the whole argument array. Arguments are often mutable, rarely implement `equals` the way you need, and make the cache grow without bound.
* Any cache in a finder must be thread-safe, because finders are called concurrently.

== Limitations

* Only interfaces can be routed.
* The router only intercepts calls made through it. When an implementation calls one of its own methods, the call goes straight to `this`.
* The finder runs on every invocation; see <<performance-and-caching>> if it's expensive.
* Reactor and RxJava return types are untested. Kotlin `suspend` functions and `Flow` are tested; see <<kotlin>>.

Routing a public interface in an exported package needs nothing extra.
If the interface is not public, or its package is not exported, open the package so the router can call the implementation:

[source,java]
----
module com.example.shipping {
    requires dev.abstraction4j.router.jdk;
    opens com.example.shipping to dev.abstraction4j.router.jdk;   // JdkAbstractionRouters
    // opens com.example.shipping to spring.core;                 // SpringAbstractionRouters
}
----

[[native-images]]
== GraalVM native images

Routers are JDK dynamic proxies, which a native image can only create if their interfaces are registered at build time.

*Automatically registered routers* (Spring Boot auto-configuration or `@EnableSpringAbstraction`) need nothing extra.
During Spring AOT processing each one contributes its proxy and reflection hints, and its bean definition is generated next to the routed interface, so non-public interfaces work too.
CI builds and runs a native image (GraalVM CE 25) of `integration-tests/native-image`, which uses an automatically registered router, manually created routers and the hints below, all routing a package-private interface.

*Routers you create yourself*, with `JdkAbstractionRouters` or `SpringAbstractionRouters` in a `@Bean` method, need hints of their own:

[source,java]
----
class RouterHints implements RuntimeHintsRegistrar {

    @Override
    public void registerHints(RuntimeHints hints, @Nullable ClassLoader classLoader) {
        // SpringAbstractionRouters: the proxy also implements Spring AOP's marker interfaces.
        hints.proxies().registerJdkProxy(AopProxyUtils.completeJdkProxyInterfaces(ShipperService.class));
        // JdkAbstractionRouters: the proxy implements only your interface.
        hints.proxies().registerJdkProxy(ShipperService.class);
        // Both routers call the implementation reflectively.
        hints.reflection().registerType(ShipperService.class, MemberCategory.INVOKE_PUBLIC_METHODS);
    }

}
----

Register it with `@ImportRuntimeHints(RouterHints.class)` on a configuration class.
Without Spring, pass the same interfaces to GraalVM's `proxy-config.json` and `reflect-config.json`.

[[kotlin]]
== Kotlin and coroutines

Routers work from Kotlin, including `suspend` functions and functions that return a `Flow`:

[source,kotlin]
----
interface ShipperService {
    suspend fun ship(@RoutingKey carrier: String, parcel: String): String
    fun track(@RoutingKey carrier: String, parcel: String): Flow<String>
}

val finder = RoutingImplementationFinder.builder(ShipperService::class.java)
    .byRoutingKey(String::class.java) { carrier -> carrier }
    .route("ups", upsShipperService)
    .otherwise(uspsShipperService)
    .build()
----

* A `suspend` function is routed like any other method. The finder runs when the call starts, on the calling thread, before anything suspends; the implementation then suspends, resumes, returns and throws exactly as if it had been called directly.
* Spring routers use Spring AOP's coroutine support. With `kotlinx-coroutines-reactor` on the classpath, Spring runs suspend functions through Reactor, which also needs `kotlin-reflect`; without it, Spring invokes them directly. Both behave the same.
* `byArgument`, `byRoutingKey` and `@RoutingKey` work on Kotlin parameters as they do in Java. A finder that reads `args` itself gets an `Array<Any?>`: an element is `null` wherever the caller passed `null`, and a `suspend` function's last element is its `Continuation`.
* `byContext` reads thread-bound context on the thread that calls the router, and coroutines move between threads. Carry the SLF4J MDC along with `MDCContext()` from `kotlinx-coroutines-slf4j`:
+
[source,kotlin]
----
MDC.put("carrier", "fedex")
withContext(Dispatchers.IO + MDCContext()) {
    shipperService.ship(null, "box")   // routed by the MDC
}
----

`./gradlew build` runs `integration-tests/kotlin-coroutines`, which covers the JDK router, a Spring router and one registered by the Spring Boot starter, with and without `kotlinx-coroutines-reactor`.

== Building

[source,shell]
----
./gradlew build                                    # format check, Checkstyle, tests, coverage and API checks
./gradlew :abstraction4j-router-benchmarks:jmh      # run the JMH benchmarks
----

`build` fails if a library module's coverage drops below 90% of lines or 80% of branches.
The coverage report is written to `build/reports/jacoco/testCodeCoverageReport/html/index.html`, and benchmark results to `benchmarks/build/reports/jmh/results.json`.

Jars are reproducible: building the same commit with the same JDK produces byte-for-byte identical jars.
Each published module also includes a CycloneDX SBOM (`<artifact>-<version>-cyclonedx.json`).
